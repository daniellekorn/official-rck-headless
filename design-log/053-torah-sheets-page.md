# 053 — Torah Sheets hub page

**Status:** accepted
**Date:** 2026-07-26
**Author:** claude-session (danielle's direction)
**Related:** #010 (Flyers collection), #031 (flyer image lightbox — Canva embed removal), #037/#038 (subcategory tags + tag groups), #007/#025 (team page taxonomy, closed-vocabulary groups)

## Background

RCK publishes three ongoing Torah sheet series — **Parsha Bytes** (weekly parsha sheet), **Dor L'Dor** (weekly sheet), and **Source Sheets** (standalone topics). None of this lives on the site today. It needs a single hub page, CMS-backed, editable by the office going forward with zero dev work per new sheet.

## Problem

Need a page that: (1) lists sheets grouped the way a learner actually browses them — by Sefer→Parsha for the two parsha-cycle series, by perek for Pirkei Avos, by topic for Source Sheets; (2) supports two different source formats per sheet (a plain PDF, or a live Canva embed) without "coming soon" placeholders — the first sheets are all PDF, but some will switch to Canva later with no further dev work; (3) matches the rest of the site's look/feel and interaction conventions exactly.

## Questions and Answers

- **Q:** Design-log #031 removed live Canva embeds site-wide because (a) no download affordance and (b) no single-page control — a multi-page design always renders in full. Doesn't this reopen both problems?
  **A:** No — both objections were specific to **flyers**, where "multi-page" was a bug (a one-page flyer shouldn't show extra pages) and there was no download story at all. Neither applies here: a source sheet is *supposed* to be a multi-page document, so rendering the whole Canva design is the correct behavior, not a limitation. And the new `canvaPdfBackup` field solves the download gap #031 flagged — the office exports a PDF from the same Canva design once, and the page gets a real Download button next to the live embed. This is a narrower, considered exception for one content type, not a reversal of #031 — #031's reasoning stays correct for flyers and stays in place there.

- **Q:** Are the "option" fields (`series`, `category`, `topic`, `sourceType`) real enum/choice fields at the Wix Data schema level?
  **A:** Wix Data collections don't enforce a native choice/enum type the way, e.g., Airtable does — every existing "option-like" field in this codebase (`Flyers.category`, `TeamMembers.roleGroup`) is a plain **Text** field with an app-side validated vocabulary, documented in `CONTRIBUTING.md` and normalized in code (see `team.ts`'s `normalizeRoleGroup`, which maps common typos/synonyms to a canonical value and falls back safely instead of dropping a row). `TorahSheets` follows the same pattern: Text fields, code-side validation, forgiving fallback. The Wix dashboard *editing UI* can still present them as a dropdown (Wix's "Text" field supports an optional predefined-values list purely for editor convenience) — that's a dashboard-only nicety, not a schema constraint the code depends on.

- **Q:** How does `Sefer` → `Parsha` grouping work if `category` only holds the Sefer name?
  **A:** The Chumash-to-parsha mapping is a fixed, closed vocabulary (54 parshios across 5 seforim, never changes) — same reasoning as `tag-groups.ts`'s DAY_TAGS/TIME_TAGS/AUDIENCE_TAGS being inferred in code rather than stored as a CMS "tag type" field. It's hardcoded in `src/lib/torah-sheets.ts` as `SEFER_PARSHIOS`, and each sheet's `subcategory` (the actual parsha name the office types) is matched against it case-insensitively. An unrecognized `subcategory` value falls back to sitting under its `category`'s "Other" bucket rather than being dropped, so a typo never silently disappears a sheet.

- **Q:** New top-level nav item — does the existing nav have room?
  **A:** Yes. Design-log #048 already handles nav overflow (a "More" collapse once items exceed the available width), so adding one more top-level link is a no-op for that mechanism.

- **Q:** Who creates the new `TorahSheets` collection — Claude via the admin API, or Danielle via the Wix dashboard?
  **A:** Asked directly in chat; answer was "try the API first." The CLI's own logged-in user token (`wix token`) turned out to lack the `DATA-COLLECTIONS-MANAGE` scope (403). The app's client-credentials token from `wix-cms-admin.ts` (design-log #052) — a different, broader-scoped credential — succeeded via `POST https://www.wixapis.com/wix-data/v2/collections`. Collection created with `TEXT`/`DATE`/`DOCUMENT`/`URL` fields per the schema below, `permissions: { insert/update/remove: ADMIN, read: ANYONE }`, matching every other public content collection on the site.

## Design

### Data model — `TorahSheets` collection (many rows)

| Field | Type | Notes |
|---|---|---|
| title | Text | Display name |
| series | Text | One of `Parsha Bytes` / `Dor L'Dor` / `Source Sheets` (exact, case-sensitive match; validated + normalized in code) |
| category | Text | For Parsha Bytes/Dor L'Dor: one of `Bereishis`/`Shemos`/`Vayikra`/`Bamidbar`/`Devarim`/`Chagim & Special Days`, plus `Pirkei Avos` for Dor L'Dor only. Unused for Source Sheets. |
| subcategory | Text | The parsha name (e.g. "Shemos"), the chag/special-day name (e.g. "Chanukah"), or the Pirkei Avos perek (e.g. "Perek Aleph"). Matched case-insensitively against the hardcoded Sefer→Parsha map; unrecognized values bucket under "Other" instead of vanishing. |
| topic | Text | Source Sheets only — e.g. `Halacha` / `Hashkafa` / `Chagim` / `Mussar` / `Tefillah`. Open-ended: sidebar groups are derived from whatever values actually appear (sorted alphabetically), same as `tag-groups.ts`'s Topic bucket. |
| date | Date | Sort key (newest first) and the date shown on each card |
| sourceType | Text | `pdf` or `canva` |
| pdfFile | Document (Media) | Used when `sourceType = pdf` |
| canvaEmbedUrl | Text (URL) | Used when `sourceType = canva` — the Canva "Publish to Web" embed URL |
| canvaPdfBackup | Document (Media), optional | A PDF exported from the same Canva design — powers a "Download PDF" button next to the live embed |

All fields the code reads are optional-safe (missing/malformed → the row just doesn't render in that bucket, never a crash), matching every other `get*()` function in `src/lib/*.ts`.

### Routing & page structure

- New route: `src/pages/torah-sheets.astro` (file-based, matches every other top-level page)
- Nav: add `{ label: "Torah Sheets", href: "/torah-sheets" }` to `baseLinks` in `Nav.astro` (between "Learn with Us" and "Community" — it's a learning resource) and to `Footer.astro`'s `quickLinks`
- New lib: `src/lib/torah-sheets.ts` — `getTorahSheets()` (single CMS query, same `wix-cms-admin` + `auth.elevate` pattern as every other lib), `SEFER_PARSHIOS` closed vocabulary, and grouping helpers (`groupParshaBytes`, `groupDorLDor`, `groupSourceSheets`) that return only the groups/subgroups that actually have ≥1 sheet — same "drop empty groups" rule as `team.ts`'s `ROLE_GROUPS` filter and `Nav.astro`'s submenu-drop.
- PDF resolution: `media.getDocumentUrl(wixDocumentUrl)` (from `@wix/sdk`, already imported for images/video in `wix-media.ts`) resolves `pdfFile` / `canvaPdfBackup` to a real URL + filename — add `resolveDocument()` alongside `resolveImage`/`resolveVideo` in `wix-media.ts`.

### Layout & interaction (matches existing conventions, no new visual language)

- `PageHeader` with `titleNavy="Torah Sheets"` + a `subtitle` intro line (prop already exists, unused elsewhere the same way — see `contact.astro`'s pattern of PageHeader + a hand-written intro paragraph below it, whichever reads better once it's in front of real copy)
- Tabs (Parsha Bytes / Dor L'Dor / Source Sheets): three pill buttons in the site's existing filter-pill visual language (`learn.astro`'s `.filter-select` treatment — white pill, gold ring when active), vanilla `data-*` + `<script>` toggle exactly like `learn.astro`'s filter bar and `team.astro`'s bio-card toggle — no new client-side pattern introduced. Deep-linkable via `#parsha-bytes` / `#dor-ldor` / `#source-sheets` (read on load, default to the first tab), matching how `Nav.astro`/`community.astro`/`team.astro` already anchor into page sections.
- Two-column layout below each tab: `lg:grid-cols-12` sidebar (`lg:col-span-3`) + results (`lg:col-span-9`) — same grid convention as `contact.astro`'s info/form split. Sidebar collapses to a `<details>` dropdown above the results on mobile, same pattern as `Footer.astro`'s mobile Quick Links disclosure.
- Sidebar: nested groups (Sefer → Parsha, or Topic) as a simple clickable list — visually a plainer sibling of `learn.astro`'s filter dropdowns, not a copy of the Denver Kollel reference's exact styling, just its information architecture (grouped, collapsible, no thumbnails).
- Results: plain card list (title, date, view/download) — no thumbnails, no `Flyer.astro`/lightbox-image pattern. Each card:
  - `sourceType = pdf` → a "View / Download PDF" link, `href` = `resolveDocument(pdfFile)`, opens in a new tab (Wix-hosted PDFs don't support a forced cross-origin download the way `Lightbox.astro`'s image download does — same honest constraint noted in #031 for images)
  - `sourceType = canva` → an inline `<iframe src={canvaEmbedUrl}>` (same bare pattern as the preserved historical Canva URLs in #031 — no `Flyer.astro` embed wrapper to resurrect) plus, if `canvaPdfBackup` is set, a secondary "Download PDF" link next to it

## Trade-offs

- PDF view/download opens in a new tab rather than downloading in place — consistent with how the rest of the site already treats Wix-hosted media downloads (accepted limitation, not new).
- Canva embeds bring back the site-wide-removed pattern for exactly one content type. Documented here explicitly so a future reader doesn't "clean this up" back in line with #031 without reading why it's different.
- Sefer→Parsha vocabulary lives in code, not CMS — matches `tag-groups.ts` precedent, but means adding a 55th "parsha" (won't happen) or changing the mapping needs a code change, not a CMS edit.

## Verification

Page renders correctly with an empty `TorahSheets` collection (each tab shows an empty-state message, no broken groups) and with populated rows across all three series/source-types; office workflow for adding a new sheet (including switching an existing row from `pdf` to `canva` with zero dev work) documented in `CONTRIBUTING.md`.

## Addendum — visual redesign, rename, and real PDF thumbnails

Follow-up pass after the office started populating real content (47 Torah Bytes sheets for תשפ״ד):

- **Renamed** `Parsha Bytes` → `Torah Bytes` (matches the actual naming already baked into the PDF filenames) and the Dor L'Dor tab now displays as "Dor L'Dor ParshaLink" — display label only, `series` still stores `Dor L'Dor`. The old `Parsha Bytes` value is kept as a normalization alias so nothing silently breaks if it resurfaces.
- **Added `year`** (Text) — the office doesn't track full dates, just wants the Hebrew year shown next to the parsha name on the card. The card list itself sorts by a fixed parsha/chag/perek reading-order comparator (commit `83cbc5b`), not by date at all.
- **Real PDF thumbnails, not Wix's auto one.** Wix's Media Manager sets a `thumbnailUrl` on every file descriptor, including PDFs — but for `DOCUMENT` media it's a generic "this is a PDF" placeholder icon, identical across every file, not a per-file page-1 render (confirmed by requesting two different PDFs' descriptors and getting the same thumbnail URL back). Real thumbnails needed a manual pipeline: download each PDF from its now-permanent Media Manager URL, render page 1 to PNG (macOS `qlmanage -t`, no extra install needed — same tool-of-convenience as `pdftoppm` in #031), upload the PNG as a normal Image file, and store it in a new **`pdfThumbnail`** (Image) field. `torah-sheets.ts` resolves it through the same `resolveImage`/`resolveImageFit` helpers every other photo field on the site already uses — no new resolution pattern.
- **Trade-off, matching #031's precedent for Flyers:** thumbnail generation is a manual step, not automatic for future sheets. A sheet with no `pdfThumbnail` just shows a plain document icon instead of a broken image — never blocks a sheet from going up. Automating this (a serverless function watching for new `pdfFile` uploads) would be the natural next step if it becomes a recurring pain point; not built now since it's a one-directional door and the current cost (a few minutes per batch) is low.
- **Layout**: replaced the boxed sidebar/card look with a flatter, list-based design (Denver Kollel's `/pdfs` page as the reference point) — hairline dividers instead of card borders/shadows, sidebar groups collapsed by default (click to expand), a persistent right-side hairline separating the sidebar from the results instead of a background box, and tab pills switched from fully rounded to the site's standard `rounded-sm` button radius.

## Addendum 2 — real thumbnails abandoned; plain PDF icon instead

Automating the real-thumbnail generation above (a Wix CLI **Event Extension** — `data.items.onDataItemCreated`, the documented mechanism for backend code that reacts to a new CMS row) was attempted and **rejected**: rendering a PDF page needs a real rasterizer, and every option requires either a native binary (`@napi-rs/canvas`, chosen specifically for being prebuilt/serverless-friendly rather than compiled like `node-canvas`) or shelling out to a system tool (`qlmanage`/`pdftoppm`, not available in a backend extension at all). Wix's build pipeline (Vite/Rollup) cannot bundle a native `.node` addon — confirmed directly: `npm run build` failed trying to parse `@napi-rs/canvas`'s compiled binary as JavaScript. A pure-JS fallback (pdf.js's SVG renderer, no canvas) was considered but not pursued once the simpler alternative below made the whole problem unnecessary. **Don't retry the native-canvas-in-an-Event-Extension approach** without a different bundling story (e.g. marking the dependency external, if Wix's CLI ever exposes that control).

Instead: PDF cards dropped thumbnails entirely. Each one is a plain PDF-icon box with a small gold download badge overlaid on it — the box itself is the link (opens the PDF in a new tab). This isn't a placeholder/fallback state anymore, it's the only state for `sourceType = pdf`, so there's no automation gap to close and no manual step for the office ever. The `pdfThumbnail` field and the 47 real thumbnails generated for the initial batch (`qlmanage`, Addendum above) were left in place rather than deleted — harmless, unread by any code path, and preserves the option to revisit real thumbnails later without having lost that work. Canva sheets were never affected by any of this — they already used a plain icon (click toggles the inline embed), which is what the redesign made PDFs consistent with.

## Addendum 3 — corrections after real content exposed three bugs

Once 47 real Torah Bytes sheets were live, actual use surfaced issues the earlier design didn't anticipate:

- **"Most recent" was wrong.** It picked whichever row Wix happened to `_createdDate`-stamp last — an artifact of the bulk-import script's insertion order, not anything meaningful. What "most recent" actually means for a running weekly series is furthest along in the reading cycle. Fixed by reversing `compareParshaOrder` itself (Devarim → Bereishis, and the last parsha of a Sefer before the first) so the card list reads most-recent-first, and picking the featured card as simply `sheets[0]` post-sort for the two parsha-based series. Source Sheets (no reading-order concept) still falls back to `_createdDate`, which is the correct signal there.
- **Clicking a card's download link filtered the sidebar to that one parsha.** A real bug, not a design gap: sidebar filter *buttons* and each card's own filter *match-target* both used the same `data-filter` attribute, so `querySelectorAll("[data-filter]")` for "find the filter buttons" also matched every card — wiring a click anywhere inside a card (download link included) up as if it were a filter selection. Fixed by renaming the sidebar buttons' attribute to `data-filter-option`, so the two roles (trigger vs. target) can no longer collide even if a future change adds more `data-filter`-bearing elements.
- **The featured card now shows a real preview after all** — reusing the `pdfThumbnail` field/images from Addendum's abandoned automation (still populated for the original 47, never deleted). Since exactly one card needs it at a time, this needed no rendering pipeline: `resolveImage()` on `pdfThumbnail` like any other photo field, rendered only when `isFeatured && pdfThumbnailUrl` is truthy, falling back to the plain icon otherwise (e.g. for a future sheet nobody's generated a thumbnail for). The earlier "no thumbnails at all" simplification held for the automation problem; it didn't need to mean *zero* real images ever.
- **Added "See More" pagination** to the unfiltered results list (roughly the first half shown, a button reveals the rest) — with dozens of sheets, requiring a long scroll to reach the sidebar filters wasn't reasonable. Only applies to the unfiltered "All Sheets" view; a specific filter always shows every match.

## Addendum 4 — "most recent" broke again once a second year of data landed; pagination redone as staged reveal

Adding the תשפ״ה batch (46 more Torah Bytes sheets, alongside תשפ״ד's existing 46) surfaced a bug Addendum 3's fix didn't anticipate: **`compareParshaOrder` has no concept of year at all** — it only ranks *where in the reading cycle* a parsha falls. תשפ״ד's `Nitzavim-Vayeilech` sits one slot later in the Devarim vocabulary than plain `Nitzavim` (see `SEFER_PARSHIOS`), so it kept outranking תשפ״ה's actual current `Nitzavim` sheet — the featured card and the top of "All Sheets" both stayed pinned to last year's row. Reproduced directly: `curl localhost:4321/torah-sheets` showed `data-filter="nitzavim-vayeilech"` on the featured card even after תשפ״ה's Nitzavim (with its own `pdfThumbnail`) was live in the CMS.

Fixed by sorting on **year first, reading-cycle position second**: `yearRank()` (new, in `torah-sheets.ts`) decodes the `year` field's Hebrew numeral via `@hebcal/core`'s `gematriyaStrToNum` (already a project dependency) — `"תשפ״ה"` → `785` — and the top-level sort in `getTorahSheets()` now does `yearRank(b) - yearRank(a) || compareParshaOrder(a, b) || a.title.localeCompare(b.title)`. A missing/unparseable year ranks lowest (`-Infinity`) rather than throwing. This makes the intended semantics explicit: within the current year, most-advanced-in-the-cycle wins (as before); across years, the newer year always wins regardless of cycle position. Confirmed fixed the same way it was reproduced — featured card now renders `data-filter="nitzavim"` with the real תשפ״ה thumbnail.

Also reworked "See More" from a single half/all toggle into a staged reveal per Danielle's request: 24 shown initially, each click adds 20 more (not "show everything"), and only once every card is visible does the button flip to "See Less" and collapse straight back to the initial 24 (with a smooth scroll back to the top of the list, since collapsing from deep in an expanded list would otherwise strand the viewport below the now-shorter list). Same `panels.forEach` structure and `data-see-more`/`data-sheet` attributes as before — no new DOM hooks, just `expanded: boolean` replaced with `visibleCount: number` and the threshold constant split into `INITIAL_COUNT = 24` / `STEP = 20`.

## Addendum 5 — closed-vocabulary gaps found adding תשפ״ו; one data typo fixed

Cross-checking the תשפ״ו batch (43 sheets) against `SEFER_PARSHIOS` before inserting anything surfaced two real gaps, caught before they shipped rather than after this time:

- **Combined-parsha vocabulary was incomplete.** `Matos-Masei` (Bamidbar) and `Nitzavim-Vayeilech` (Devarim) were already in the list from earlier batches, but `Behar-Bechukosai` and `Achrei Mos-Kedoshim` (both recurring again in תשפ״ו, and already silently wrong in the תשפ״ה batch — see below) were never added, and תשפ״ו introduces two more combined designs with no existing entry at all: `Tazria-Metzora` and `Vayakhel-Pekudei`. A sheet titled with a combined name that isn't in the vocabulary doesn't error — it just silently falls into the sidebar's "Other" bucket and sorts to the *end* of its Sefer (rank via `subIndex === -1`), which is exactly backwards for a sheet that should read as one of the more recent entries in that Sefer. Added all four to `SEFER_PARSHIOS`, each inserted between its two component parshios (same slot `Matos-Masei` and `Nitzavim-Vayeilech` already used) — not a vocabulary rename, just completing a pattern the vocabulary was already committed to.
- **`Shemini` (תשפ״ה CMS row) never matched anything.** The vocabulary has always spelled it `Shmini` (no middle "e" — standard Ashkenazi transliteration, e.g. "Shmini Atzeres"); the CMS row was entered as `Shemini` and so it too has been sorting into "Other" since the תשפ״ה batch went up. Fixed by correcting the CMS row's `title`/`subcategory`, not the vocabulary.

Neither bug crashed anything or was visible without deliberately checking the "Other" bucket / reading order — worth remembering that a mistyped or newly-combined title fails silently here, not loudly.

## Addendum 6 — featured-sheet rule redefined: single upload vs. batch, calendar-aware; old thumbnails auto-cleared

Danielle's own read of "most recent" once real multi-year data existed didn't match Addendum 4's fix. Adding the תשפ״ו batch (43 sheets, sorted by year+reading-cycle) featured `Haazinu` — furthest along in the reading cycle among what was in the batch — but that's months away from the real current week; she wanted `Vaeschanan` (the parsha actually read this past Shabbos, per the real Hebrew calendar). New rule, in her words: *"the most recently uploaded Torah sheet should take the place of the first one on top with a preview. Unless there is a batch upload, in which case it should be the most recent parsha."*

Implemented as `pickFeatured()` in `torah-sheets.ts`:
- **Single new upload** (its `_createdDate` isn't within `BATCH_WINDOW_MS` — 30 min — of any other row's) → that row is featured immediately. No calendar logic; it's simply the newest thing added.
- **Batch upload** (several rows landing within that window, e.g. a season's worth of PDFs bulk-imported at once) → featured is whichever sheet in *that batch* matches the real current Hebrew-calendar parsha, computed via `@hebcal/core`'s `HDate`/`Sedra` from the actual system date (most recently *completed* Shabbos, not the upcoming one — a Torah Bytes sheet reviews a parsha already read). hebcal's own parsha spellings (`Vaetchanan`, `Bereshit`, etc.) differ from this site's Ashkenazi vocabulary, so `HEBCAL_TO_SITE_PARSHA` translates them; a combined hebcal name with no direct site match falls back to matching either half (handles a year where hebcal combines a pair the office ran as separate sheets). If nothing in the batch matches at all (chag-only Shabbos, or the batch just doesn't cover the current week), falls back to the old furthest-along heuristic rather than featuring nothing.
- The featured sheet is also spliced to the front of `tab.sheets` in `torah-sheets.astro` (`orderTab`) — previously featuring = "whatever the reading-order sort already put first," so no reordering was needed; now that the featured pick can diverge from that sort, the list order has to be forced to match.

**Verified against the real scenario that prompted this**: today's real date resolves (via `node -e` against `@hebcal/core`) to 14 Av 5786, most recent Shabbos 11 Av → `Vaetchanan` → `Vaeschanan`, present in the תשפ״ו batch → featured. Confirmed via `curl localhost:4321/torah-sheets`.

**Also new**: whenever a new sheet becomes featured and gets a real thumbnail, every other Torah Bytes sheet's `pdfThumbnail` is now cleared (CMS field + the underlying Media Manager file, where it lives in this site's own media namespace) — Danielle's rule, "to keep the website clean and not have old images there for [no] reason." This reverses Addendum's original "leave old thumbnails in place, harmless" call now that thumbnails are deliberately single-use rather than a batch-generated set. Applied once by hand to clear the 12 thumbnails that had accumulated (`Haazinu`, `Nitzavim`, and 10 from the original תשפ״ד batch) down to just the new featured sheet — going forward this needs to happen manually alongside each new featured pick until/unless it's automated. **Important scoping correction from Danielle**: this clearing is per-series only — adding a new featured item to one series (e.g. Source Sheets) must never clear another series' (e.g. Torah Bytes') thumbnails.

## Addendum 7 — Source Sheets' first topic exposed a batch-featured bug; default landing tab changed

Adding the first `Source Sheets` topic ("From Iyun to Halacha", 9 PDFs bulk-inserted seconds apart) surfaced a bug that never showed up for Torah Bytes/Dor L'Dor: `pickFeatured`'s batch tie-break (once calendar-match fails) fell through to `compareParshaOrder`/title — but Source Sheets rows have no `category`, so they all tie into the same catch-all bucket and the pick becomes alphabetically-first-by-title, not newest. Same root cause in `getTorahSheets()`'s base `.sort()` meant the plain card-list order for Source Sheets (and the "All Publications" tab) was alphabetical too, not upload-recency.

Fixed both: `pickFeatured` now special-cases a batch where every row lacks `category` (no reading-order concept at all) and picks by newest `_createdDate` there instead of falling to the parsha-order fallback. A new `sortByUploadRecency()` export orders by newest `_createdDate` first (missing dates last); applied to the "all" and "source-sheets" tabs' flat card lists specifically — Torah Bytes/Dor L'Dor keep the original year+reading-cycle sort, since upload-recency there is exactly the bug Addendum 3/4 already fixed.

Also confirmed: the featured card's real preview image isn't automatic — it still needs a manually-generated `pdfThumbnail` (same `qlmanage -t` pipeline as the original batch) even after the ordering/pick logic is correct; without one the featured row is just the plain icon at a larger size.

Separately, the default landing tab (no URL hash) changed from "whichever tab is first in the `tabs` array" (previously `All Publications`, incidentally) to an explicit `DEFAULT_TAB_KEY = "torah-bytes"` constant, kept in sync by hand between the Astro SSR panel-visibility check and the client `<script>`'s hash-fallback (both hardcode the literal — this codebase's client scripts don't share Astro frontmatter constants across that boundary).

**Verification:** confirmed via `curl localhost:4321/torah-sheets` — Torah Bytes panel renders non-hidden by default; the Source Sheets panel's 9 cards render newest-`_createdDate`-first with the top row carrying a real `sheet-thumb--preview` image once its `pdfThumbnail` was set.

## Addendum 8 — `category` becomes a multi-value array; first Dor L'Dor batch (30 sheets)

Dor L'Dor's first real batch (30 "ParshaLink"-titled sheets) included several designs that intentionally combine a parsha with Pirkei Avos and/or Chagim & Special Days (e.g. "Pinchas / Shiva Asar B'Tammuz – Consistency" spans Bamidbar + Pirkei Avos + Chagim). Previously (design-log #053's original scope-rules precedent for Torah Bytes) a parsha+chag combo became **two separate CMS rows** sharing one `pdfFile`; Danielle asked instead for `category` to become a real multi-value field so **one row** can carry all its tags and surface under every matching sidebar filter — no more row-splitting for this case.

- **Schema**: `category` changed from `TEXT` to `ARRAY_STRING` via `PatchDataCollectionField` (existing values aren't auto-migrated on a type change — confirmed via the API's own doc string — so all 137 existing rows had their single string value bulk-wrapped into a one-element array via `BulkPatchDataItems`, `SET_FIELD` action, before inserting anything new).
- **Code** (`torah-sheets.ts`): `TorahSheet.category` is now `string[]`. New `hasCategory(sheet, label)` helper (`some()` over the array) replaces every single-value `===` comparison in `compareParshaOrder`, `groupBySeferAndChagim`, `groupDorLDor`, `groupAllSheets`, and `pickFeatured`'s category-less-batch check. A multi-category sheet's **reading-cycle sort rank** is still decided by its Sefer tag first (falling back to Chagim, then Pirkei Avos, only when there's no Sefer tag at all) — a sheet doesn't get ranked multiple ways depending on which filter you're viewing it through.
- **Deliberate scope limit — `subcategory` stayed a single string**, not an array. Danielle only asked for `category`; a combo sheet's `subcategory` is set to its primary parsha identity (e.g. "Pinchas"), so it slots correctly under its Sefer's own parsha subgroup, but under Chagim & Special Days it surfaces as its own same-named group (e.g. a "Pinchas" button under a "Chagim & Special Days" heading, not "Shiva Asar B'Tammuz") since Chagim bucketing has no vocabulary restriction — cosmetically imperfect but functionally correct (the button still reveals the right card). Under Pirkei Avos it lands in that bucket's existing "Other" group instead of a specific perek, for the same reason. Revisit only if Danielle asks for precise per-category subcategory labels.
- **Reused, not rebuilt**: `groupDorLDor`, `pickFeatured`, `orderTab`'s featured-splice, and the client script's "See More" pagination (`INITIAL_COUNT`/`STEP`) needed zero new code for Dor L'Dor — they're the exact same calls already used for Torah Bytes, just now operating on `series === "Dor L'Dor"` rows with multi-value categories.

## Addendum 15 — main PDF click: opens in a new tab *and* saves under the right name

Addendum 14 reverted the main click to a plain URL to stop it auto-downloading, but that meant a visitor who *does* save from the opened tab is right back to a meaningless CDN-hash filename (Addendum 12's original complaint) — Wix's document CDN genuinely offers no middle ground: a plain URL opens inline with no filename control, `?dn=` gets a filename but forces an outright download (`Content-Disposition: attachment`), confirmed via curl and via the Wix SDK docs (no `inline`-with-filename option exists for a resolved document URL). Danielle asked for both at once: open in a new tab, but save under the right name if downloaded from there.

- **Approach**: client-side fetch → `Blob` → wrapped in a `File` (`new File([blob], "RCK.{Publication}.{Title}[.{Year}].pdf", { type: "application/pdf" })`) → `URL.createObjectURL(file)` → navigate a new tab to that blob URL. A browser's PDF viewer uses the `File.name` as the suggested filename if the visitor saves from within it — no server cooperation needed, unlike Addendum 12's approach. `pdfUrl` stays the plain resolved URL (works as the `href` fallback for no-JS/blocked-fetch); `pdfFilename` (previously the raw, unused Wix-stored name) now holds the computed `RCK.*` name specifically for this purpose, exposed to the client as `data-pdf-name`.
- **A real bug, caught only by testing in an actual browser — not skippable next time.** The Chrome extension bridging this session to a live browser still wasn't connected, so a temporary `playwright-core` + Chromium install (`npm install --no-save playwright-core && npx playwright install chromium`, both removed again after) stood in for it. First implementation opened the blank tab via `window.open("", "_blank", "noopener")` — per spec, `window.open` returns `null` whenever `noopener` is passed, so the later `tab.location.href = objectUrl` assignment silently no-op'd (guarded by `if (tab)`), leaving every opened tab stuck on `about:blank` forever. Dropping `noopener` from *this specific* call (not a tabnabbing risk here — the tab only ever shows this site's own blob: content or the plain CDN URL, never attacker-controlled content) fixed it immediately, confirmed by the same test going from "tab never loads" to "tab shows the fetched PDF."
- **A second false alarm, also only resolvable by testing**: the fix initially looked broken in headless Chromium specifically — navigating to a PDF-typed blob: URL fired a `download` event instead of rendering inline, in both the `location.href` and the `iframe src=` variants tried as a fix. Retesting with `headless: false` showed *neither* variant actually has this problem — headless Chromium simply doesn't ship a working PDF viewer, so it treats anything it can't render as a download; real Chrome (any platform) doesn't. Kept the simpler `location.href` approach (no iframe wrapper needed) once headed testing confirmed it worked correctly.
- **Verification**: full click-through in headed (real, non-headless) Chromium against the actual unmodified site code — `context.route()` redirected the currently-unreachable-from-this-sandbox Wix CDN host to a tiny local stand-in server mirroring its real headers (`access-control-allow-origin: *`, `content-type: application/pdf`, no `Content-Disposition` — matching values confirmed via curl against the real host earlier in this session) — clicking the real `[data-pdf-open]` link opened a new tab that navigated to `blob:http://localhost:4321/...`, with zero `download` events. All temporary test scripts, the stand-in server, and `playwright-core` were removed after; nothing test-related was committed.
